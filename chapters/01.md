# 第一章

## 原文

> 道可道，非常道。名可名，非常名。
> 无名，天地之始；有名，万物之母。
> 故常无欲，以观其妙；常有欲，以观其徼。
> 此两者，同出而异名，同谓之玄。玄之又玄，众妙之门。

断句说明：第三句取"常无欲 / 常有欲"的读法。帛书本作"恒无欲也，以观其眇；恒有欲也，以观其所噭"，支持这一读法。另一种读法"常无，欲以观其妙"会把主语换成"无 / 有"本身，映射出来的东西不同，本章不采用。

## 概念

| 概念 | 原义 | 在代码中 |
|---|---|---|
| 道 | 先于一切描述而存在的实在 | 分两种。**机器之道**：系统在运行时的真实行为。**业务之道**：现实业务本身。调试类任务看机器之道，设计类任务看业务之道。两者都不是文档、类型或架构图，那些只是对道的描述 |
| 名 | 对实在的切割与指称 | 一切定名的动作：类型、表、列、接口签名、枚举值、状态标签、指标名。每一个名都是在领域上划一刀 |
| 无名 | 尚未被切割的混沌 | 还没建模的原始材料：用户的一句话、一条原始事件、一段 raw text、一个字节流 |
| 有名 | 切割之后的万物 | 建模之后的实体：schema、type、module。一切功能都由它们组合而成 |
| 无欲 | 不带目的地看 | 观测模式：profiling、读原始日志、看 telemetry，不带假设 |
| 有欲 | 带着目的去看 | 设计模式：手里有一个具体需求，去定边界 |
| 妙 | 无欲时看见的东西 | 系统实际的运作机理 |
| 徼 | 有欲时看见的东西 | 接口契约、约束、极限 |
| 玄 | 两股拧成一根绳 | 无与有、原始与派生，是同一份实在的两个阶段，拧合在一起但各是各的。拧合有主从：名服从道 |

## 逐句

### 道可道，非常道

**翻译：** 对行为的任何描述都是有损的。

**理解：** 架构图、类型签名、设计文档、设计原则，都是对系统行为的快照。快照一定丢信息，而且拍下来的那一刻就开始过期。能被写下来的设计（可道之道）都不是最终设计（非常道）。这不是说不要写，而是说不要把写下来的东西当成系统本身。

**例子：**

- 架构图上请求从网关到服务 A 再到数据库。真实路径里还经过了一个没人画上去的缓存层，它在某种条件下返回旧数据。图是可道之道，缓存的行为是道。
- 函数签名声明它是纯函数。它内部写了一行日志，日志库在磁盘满时会阻塞。签名是可道之道。
- 设计第一天就试图写出"包罗万象、预测未来所有需求"的终极框架。这是把可道之道当成常道。

**推论：**

1. 只为当前已陈述的需求建模。不为想象中的未来需求预留表、列或抽象。
2. 文档、类型与运行时行为不一致时，错的是文档和类型。先改描述，再谈改行为。

### 名可名，非常名

**翻译：** 对结构的任何切割都是临时的。

**理解：** 和上一句平行。上一句讲对行为的描述有损，这一句讲对结构的切割临时。名把连续的领域切成离散的符号。这一刀必须切，否则万物无从生；但它是在某个时刻、为某个目的切的，领域变了它就过期。名字不是领域本身。

**例子：**

- `user` 表创建时指"一个登录的人"。后来产品加了组织账号，有人往 `user` 表里塞了 `is_org` 列。名已经不对应实了，为了省一次迁移而假装它还对应。
- `message` 表开始装 tool call、系统提示、函数返回值。每一种都和"用户或助手说的一句话"不是同一种事物。
- `status` 枚举从三个值长到十四个，其中一半是历史遗留。一个封闭集合在声明"此物只有这几种"，而领域从不同意。
- `importance` 列。它取决于谁在什么时候用什么标准判的，是所有名里最不"常"的，却被存成了和 `created_at` 同等地位的列。

**推论：**

1. 一个名字只承载它被创建时所指的那一种事物。领域变了，重切，不往旧名字里塞新含义。
2. 越是结论，越不是常名。事实类的列（`created_at`、`content`、`parent_id`）相对稳定；结论类的列（`importance`、`category`、`is_relevant`、`sentiment`）只能作为可重建的派生物存在，不进 source of truth。
3. 封闭集合（enum、status 列）是最强的常名断言。优先存发生了什么（事件），状态作为派生。
4. 结论不是事实，但做出结论这个动作是事实。"某次调用陈述了 X" 可以作为事件进入原始层，前提是只记陈述本身（谁、何时、原话），不记它的真值或权重；当前有效的结论仍然只能从这些事件派生，不能存。这一条不在规则块里：2026-11-07 评测中，agent 在没有它的情况下自行得出了这个结构（见 eval/runs/2026-11-07/REPORT.md）。

### 无名，天地之始；有名，万物之母

**翻译：** 系统从未建模的原始材料开始；建模之后的实体是一切功能的来源。

**理解：** 两句都是肯定句，没有褒贬。无名是起点：任何系统在第一刀切下去之前，只有原始材料。有名是母体：切出来的实体是一切后续功能生长的基础。两者缺一不可。错的不是切，是忘了自己是从哪里切出来的。

**例子：**

- 一个日志系统的天地之始是一行行原始文本。切出 `level`、`service`、`trace_id` 之后，告警、面板、追踪才从这些字段里长出来。
- 一个电商系统的天地之始是"某人在某时对某物做了某事"。订单、库存、账单是从这些事件里切出来的有名之物。
- 一个聊天应用的天地之始是用户说的一句话。`message` 表是母，所有记忆、摘要、画像都从它生出来。

**推论：**

1. 设计顺序：先列出系统会记录到的原始事实，再从中导出表。不先想表再往里塞字段。

### 常无欲，以观其妙；常有欲，以观其徼

**翻译：** 不带目的地观测，看到的是机理；带着目的设计，看到的是边界。

**理解：** 这是两种姿态，各有各的产出。无欲是观测姿态：不带假设去读数据、读日志、看指标，看到的是系统实际怎么运作（妙）。有欲是设计姿态：手里有一个具体需求，去定接口、约束、极限（徼）。两种姿态都要，但不能同时。带着"应该"去看数据，看到的只是自己的假设。

**例子：**

- 看 p99 延迟之前先认定"应该低于 200ms"，然后在数据里找证据。这是有欲地观测，看不到妙。正确的做法是先看分布长什么样，再问为什么。
- 指标"测试覆盖率必须 100%"、"所有查询必须上缓存"。脱离上下文的好坏标签是预期，不是观测。
- 有了一个具体需求"用户要能撤回消息"，这时候才去定边界：撤回是删除还是追加一条撤回事件，撤回后别人还能不能看到，撤回有没有时限。这是有欲观徼，产出的是契约。

**推论：**

1. 观测时不带好坏预期。任何关于速度、规模或成本的断言都带一个数字，或者明说"未知"。写成原则而不是禁词清单：清单会被绕过，第一轮评测里就有 agent 写出了 "cost nothing"。
   - 已给出的数字不是未知。2026-11-07 加压评测里，任务写明 5e9 行，三次运行仍把分区推到"下一步，阈值待测"。"未知"是对没有数字的事说的，不是对已经给了数字的事说的。规则措辞暂不动，先记在这里，等第二个任务上再出现时改。
2. 设计时每个表要说明它记录的是哪一种事实、谁拥有它；每个列要说明它是事实、引用还是派生值。
3. 两种姿态交替进行：先无欲观（摆出原始材料，不带方案），再有欲名（切出实体和边界），再回到原始材料对照一遍。

### 此两者，同出而异名，同谓之玄。玄之又玄，众妙之门

**翻译：** 原始与派生是同一份实在的两个阶段，拧合在一起但各是各的；拧合逐层发生；只要原始层还在，就随时能回去重看、重切。

**理解：** 玄的古意是两股拧成一根的绳。无和有、原始和派生，不是两样东西，是同一件事的前后两刀。拧在一起，但两股仍然各是各的；而且拧合有主从，名服从道。"玄之又玄"说拧合不是一次，是逐层：这一层的产出是下一层的原料。"众妙之门"说这个循环是看见一切机理的门，而门开着的前提是原始层还在。

**例子：**

- 一条 summary 概括了二十条 message。summary 是有名，message 是它的无名。summary 必须能指回那二十条，否则它是一个没有来源的断言。
- 不在 `messages` 上加 `summary` 列，不通过改写 message 来"更新记忆"。两股绳各是各的。
- message 之于 summary 是无名，summary 之于 user profile 又是无名。删掉所有 summary 和 profile，从 message 重建，系统不丢失任何事实。反过来永远不成立。
- 很多记忆系统总结完就把原文扔掉，只留摘要。那一刻门就关了，以后只能透过当时那一刀看世界，而那一刀是非常名。

**推论：**

1. 派生物必须能指回它的来源。provenance 是外键，不是注释。
2. 原始层和派生层分表。原始层只追加不修改，派生层另立。
3. 任何派生层都能从它下面那一层整个删掉重建，方向只有一个：向上。
   - 这条有代价：原始层不能指向派生层，于是"某次调用用了哪些记忆"记不下来，除非把全文快照进原始层。2026-11-07 加压评测里 agent 算出全文快照约 80 TB，于是放弃了审计；baseline 三次都留了 id 列表。规模一大，第 11 条就在用可审计性换可重建性。哪一边更贵由任务决定，这里只记下它不是免费的。
4. 原始层永不因为派生而被删除或压缩。

## 规则（中文草稿）

以上推论的汇总，供编译成给 agent 的英文规则块。编译时要去掉领域特定的例子，规则本身必须对任何系统成立。

1. 只为当前已陈述的需求建模。不为想象中的未来需求预留表、列或抽象。
2. 文档、类型与运行时行为不一致时，错的是文档和类型。（2026-11-07 schema 评测：无效果，无噪音；待调试类任务验证）
3. 一个名字只承载它被创建时所指的那一种事物。领域变了，重切。
4. 结论类的值（评分、分类、标签、相关性）只能作为可重建的派生物存在，不进 source of truth。
5. 优先存发生了什么，状态作为派生。对封闭集合（enum）保持怀疑。
6. 先列出系统会记录到的原始事实，再从中导出结构。
7. 观测时不带好坏预期。任何关于速度、规模或成本的断言都带一个数字，或者明说未知。（2026-11-07 加压评测：已给数字时仍说"未知"，见无欲一节）
8. 每个表说明它记录哪一种事实、谁拥有它；每个列说明它是事实、引用还是派生值。
9. 派生物必须能指回它的来源，用外键而不是注释。（2026-11-07 schema 评测：baseline 三次都自发做到，效果未验证）
10. 原始层与派生层分表。原始层只追加不修改。
11. 任何派生层都能从下一层整个重建，方向只向上。（2026-11-07 加压评测：规模下以审计换重建，见玄一节）
12. 原始层永不因为派生而被删除或压缩。
